# HALO Mission Archive Tool

This repository contains the ground-computer tools used to create, identify, populate,
and preserve a HALO drone mission archive. The archive keeps the mission configuration,
software state, ReSpeaker recording, PX4 ULogs, status diagnostics, processing products,
and operator notes together under one canonical mission ID.

The ground archive is the permanent record. The matching folder on the drone is a
staging and recording location that is copied back after the mission.

> **Archive rule:** never reuse, rename, or overwrite a mission folder after data has
> been collected. Back up the complete mission folder as one unit.

## The canonical mission ID

Every mission has one `mission_id`. The same value is used for:

- The ground archive folder name.
- The drone-side ReSpeaker/session folder name.
- The `mission_id` passed to the automated drone mission agent and its recorder.
- The `mission_id` stored in `metadata/mission_metadata.json`.
- The default remote source selected by `collect_drone_data.py`.
- The local audio/session folder created during collection.

When no fixed ID is supplied, the ground computer generates one in this form:

```text
YYYYMMDD_HHMMSS_UTC_<sanitized-mission-name>_<drone-id>
```

For the included `D0012` configuration, an example is:

```text
20260820_143000_UTC_audio_px4_sync_test_D0012
```

The canonical paths for that example are:

```text
Ground: ~/MIC_ARRAY_ROS/HALO_ARCHIVE/20260820_143000_UTC_audio_px4_sync_test_D0012/
Drone:  root@192.168.0.20:/home/root/halo_sync_test/20260820_143000_UTC_audio_px4_sync_test_D0012/
```

`run_halo_mission.py` obtains the generated ID from `create_mission_archive.py` and
passes it to the drone agent automatically. A fixed ID can still be supplied to the
standalone creator with `--mission-id`; fixed IDs may contain letters, numbers,
periods, underscores, and hyphens only.

- `scripts/run_halo_swarm_mission.py` is the multi-drone ground entry point; it uses

- `scripts/__pycache__/`, when present, is generated by Python compilation and is not

```text
│   ├── ulog_candidates_remote.txt                  # when ULogs are auto-discovered
│   ├── next_commands.sh                            # standalone recovery guide
│   └── <mission_id>_collection_manifest.json       # after collection
├── drone_data/
│   ├── audio/
│   │   └── <mission_id>/                           # complete copied drone mission
│   │       ├── audio/respeaker_6ch.wav
│   │       ├── bags/

│   ├── px4_logs/
│   │   └── *.ulg                                   # explicit or auto-selected ULogs
│   ├── ros_bags/                                   # designated bag storage
│   ├── raw_sensor_data/                            # other unmodified inputs
│   └── status_logs/
│       ├── <mission_id>_remote_status_snapshot.json
│       └── <mission_id>_drone_code_state.json
├── processed/
├── plots/
└── reports/
```

### Why each directory exists

| Location | What belongs there | Why it is separate |
| --- | --- | --- |
| `README.md` | Human-readable mission identity, paths, configuration, status, and preservation notice | Lets a person understand the archive without opening JSON |
| `config/` | Exact drone and flight-profile YAML files used for the mission | Preserves configuration provenance even if repository templates later change |
| `metadata/` | Code state, mission state, generated next commands, collection history, command results, warnings, errors, notes, and termination reason | Keeps machine-readable provenance and audit information together |
| `drone_data/audio/<mission_id>/` | The complete folder copied from the drone sync root, including ReSpeaker output and any session-side metadata | Preserves the remote session as collected |
| `drone_data/px4_logs/` | PX4 `.ulg` files explicitly requested or automatically selected from remote candidates | Keeps flight-controller logs separate from audio and derived files |
| `drone_data/ros_bags/` | ROS 1 or ROS 2 bag files | Gives large message recordings a predictable raw-data destination |
| `drone_data/raw_sensor_data/` | Other original sensor exports that do not belong to audio, ULogs, or bags | Prevents raw inputs from being mixed with processed results |
| `drone_data/status_logs/` | Drone service, ULog-listing, OS, and code/service snapshots | Makes post-flight diagnosis possible even after the drone state changes |
| `processed/` | Derived CSV, synchronized timelines, extracted ULog fields, calibrated audio, and similar products | Keeps reproducible derivatives separate from immutable raw inputs |
| `plots/` | Figures and visual diagnostics generated from processed data | Keeps presentation artifacts out of raw and processed datasets |
| `reports/` | Mission summaries, analysis reports, and final deliverables | Provides a stable location for conclusions and review material |

Raw files should remain unchanged. If data needs cleaning, conversion, synchronization,
or filtering, write the result under `processed/` and leave the source under
`drone_data/` intact.

## Drone mission folder layout

With `--initialize-drone`, the creator uses SSH and rsync to prepare:

```text
/home/root/halo_sync_test/<mission_id>/
├── README.md
├── config/
│   ├── D0012.yaml
│   └── audio_px4_sync_test.yaml
├── audio/
│   └── respeaker_6ch.wav
├── bags/
│   └── rosbag2_<UTC timestamp>/
├── metadata/
│   ├── mission_metadata.json
│   ├── drone_agent_start.json
│   ├── drone_agent_status.json
│   ├── drone_agent_final.json
│   └── termination_reason.txt
├── px4_logs/
└── status_logs/
```

The remote folder name must exactly equal the ground folder name. The ReSpeaker sync
recorder must receive the same value as its `session_id`, so its output lands under the
correct mission folder.

PX4 writes ULogs under `/data/px4/log`, not under the mission sync folder. Every
collection saves the ten newest remote candidates. Explicit `--ulog` paths take
precedence; otherwise automatic selection only considers candidates whose modification
time is at or after the recorded mission start. `--no-auto-ulog` saves candidates
without copying one.

## What is captured in metadata

### `metadata/code_state.json`

This is the base-station software snapshot taken before archive output is created. It
contains:

- Ground-computer hostname and username.
- UTC capture time, current working directory, and optional explicit `code_root`.
- Git repository root, branch, full commit hash, and `git status --short` output.
- If `--code-root` is supplied, Git discovery is performed from that directory only.
- A Boolean `has_uncommitted_changes` flag.
- Python version.
- Absolute path and SHA-256 hash of the running archive-creation script.
- Capture warnings, including a clear warning when no Git repository is available.

The scripts inspect Git only. They never stage or commit files automatically.

### `metadata/mission_metadata.json`

This is the authoritative mission record. It includes:

- `mission_id`, mission name, drone ID, operator, and UTC creation time.
- Ground and drone mission paths.
- The ReSpeaker session ID.
- Archived configuration paths and the selected `code_root`.
- SSH preflight result when drone initialization was requested.
- Path to the generated `metadata/next_commands.sh` operator guide.
- A short base-station code-state summary and link to `code_state.json`.
- Expected output status.
- Drone-initialization command results when requested.
- A `run_status` section containing current state, warnings, errors, collection status,
  and termination reason.
- A `collections` list containing each recorded collection attempt, copied paths,
  notes, warnings, errors, and timestamps.

### `metadata/<mission_id>_collection_manifest.json`

The collection manifest records the operational details of the latest collection run:

- Canonical `mission_id` and effective `session_id`.
- Local ground mission and audio folders.
- Canonical and effective remote drone folders.
- Collection start and finish times.
- Every rsync and SSH command, return code, standard output, standard error, and success
  flag, plus the initial SSH connection check.
- Copied ReSpeaker/session and ULog paths.
- ReSpeaker WAV existence and byte size.
- Automatic ULog candidates, selection, and copy result when no `--ulog` is supplied.
- Remote status and drone code-state paths.
- Operator notes, termination reason, warnings, and errors.

Running collection again for the same mission rewrites the named collection manifest
and status snapshot files. The mission metadata still appends a collection record. For
the cleanest archive, collect once after confirming all desired ULog paths; if repeated
collection manifests must be preserved individually, copy the previous manifest before
rerunning.

## Drone status snapshots

Collection always attempts a general remote status snapshot containing:

- A time-sorted listing of recent `.ulg` files found under `/data`.
- `voxl-inspect-services` output filtered for PX4, MAVLink, ROS, DDS, microDDS, and XRCE.

Unless `--skip-drone-code-state` is supplied, collection also attempts:

- `hostname`
- `date`
- `uname -a`
- `voxl-inspect-services` filtered for PX4, MAVLink, and microDDS
- `systemctl status voxl-px4 --no-pager`
- `systemctl status voxl-microdds-agent --no-pager`

Unavailable commands or inactive services are recorded as warnings. Transfer failures
are recorded as errors. Full command output remains in JSON even when the concise
terminal message shows only the first failure line.

## What is automatic and what is not

| Operation | Automatic? | Notes |
| --- | --- | --- |
| Generate the canonical mission ID | Yes | Unless `--mission-id` is supplied |
| Create the ground archive structure | Yes | Always performed by the creator |
| Copy drone/profile YAML into the ground archive | Yes | Always performed by the creator |
| Record base-station Git and script state | Yes | Use `--code-root` when the repository is outside automatic discovery |
| Run the full record/monitor/collect lifecycle | Yes | Use `run_halo_mission.py` |
| Generate standalone recovery commands | Yes | Written to `metadata/next_commands.sh`; never runs automatically |
| Check SSH before a batch of remote actions | Yes | Clear failure before the batch; password login remains supported |
| Create the matching drone folder | Optional | Requires `--initialize-drone` |
| Copy README, metadata, and config files to the drone | Optional | Performed with drone initialization |
| Start and stop ReSpeaker recording | Yes in automated runs | The drone agent owns `arecord` and clean finalization |
| Record ROS2 bags | Optional in automated runs | Use `--enable-rosbag`; missing ROS2 topics become warnings |
| Monitor disarm/failsafe/flight-state loss | Best effort | Uses visible `/fmu/out/vehicle_status`; duration is the fallback |
| Arm, fly, or disarm the drone | No | Flight execution remains a separate safety-controlled operation |
| Copy the complete remote mission folder | Yes during collection | Audio, metadata, bags, status logs, README, and config are copied with rsync |
| Copy PX4 ULogs | Yes | Explicit paths win; otherwise only the newest candidate from the mission time window is eligible |
| Record drone status snapshots | Yes during collection | Drone code-state capture can be skipped explicitly |
| Record termination reason and notes | Yes | Agent/orchestrator and collector metadata preserve them |
| Transfer other raw sensors | No | Store/copy them into `drone_data/raw_sensor_data/` explicitly |
| Process data, make plots, or write reports | No | Put derived outputs in the designated directories |
| Commit anything to Git | No | Git access is read-only |

The presence of `ros_bags/` or `raw_sensor_data/` does not prove that those products
were recorded. Verify their contents before considering a mission archive complete.

## Prerequisites

The ground computer needs:

- Python 3.10 or newer for the ground-side creator, collector, and orchestrator.
- Python 3.6 or newer on the drone for `halo_drone_mission_agent.py`; the agent avoids
  postponed annotations, modern generic/union syntax, `text=True`, and `shlex.join`.
- `ssh` and `rsync` available on `PATH`.
- Network access to `192.168.0.20`.
- Authentication for `root@192.168.0.20` or the confirmed `halo-d0012` SSH alias,
  preferably using an SSH key.
- Drone-side `arecord` for audio; ROS2 CLI only when ROS2 bag/flight-state data is expected.
- Git if branch/commit information is expected.

The scripts use only Python standard-library modules. YAML files are copied and the
simple top-level `drone_id` value is read without requiring PyYAML. SSH key login is
recommended because initialization and collection each use several independent SSH or
rsync connections. See [SSH key setup](docs/SSH_KEY_SETUP.md); the Python scripts never
create keys or edit the user's SSH configuration.

Useful preflight checks:

```bash
cd ~/MIC_ARRAY_ROS/HALO_ARCHIVE_TOOL

python3 -m py_compile scripts/create_mission_archive.py
python3 -m py_compile scripts/collect_drone_data.py
python3 -m py_compile scripts/halo_drone_mission_agent.py
python3 -m py_compile scripts/run_halo_mission.py

ssh root@192.168.0.20 "LC_ALL=C LANG=C hostname && date"
rsync --version
```

## Automated mission workflow (recommended)

The production workflow does not require manual `arecord` commands or manual file
copying. See [Automated mission workflow](docs/AUTOMATED_MISSION_WORKFLOW.md).

For a short home audio-only, no-arm test:

```bash
python3 scripts/run_halo_mission.py \
  --mission-name "home_hotspot_audio_auto_test_002" \
  --operator "Victor Basvi" \
  --drone drones/D0012_home_temp.yaml \
  --profile profiles/audio_px4_sync_test.yaml \
  --drone-host halo-d0012-home \
  --code-root ~/MIC_ARRAY_ROS/HALO_ARCHIVE_TOOL \
  --duration 30 \
  --enable-audio \
  --no-auto-ulog
```

The orchestrator first runs the uploaded agent's `--help` using the drone's Python.
It launches only after that check passes, then waits for the process to remain alive
and produce `drone_agent_start.json` or `drone_agent_status.json` before reporting
startup confirmation. Audio-only mode disables automatic ULog copying by default;
`--auto-ulog` is the explicit override.

For a ReSpeaker/PX4 test, add `--enable-rosbag`. Wait until ground status reports
`audio=True`, then arm and disarm manually under the approved procedure. The drone
agent finalizes after disarm and the ground orchestrator invokes collection
automatically. These scripts never arm or disarm the drone.

## Standalone archive and recovery workflow

The following creator/collector sequence is retained for diagnostics and recovery. It is
not the recommended operational workflow and does not replace the automated orchestrator.

The legacy standalone sequence and bench/flight safety notes are also in
[the recovery workflow guide](docs/WORKFLOW.md).

### 1. Create the ground archive and initialize the drone

```bash
cd ~/MIC_ARRAY_ROS/HALO_ARCHIVE_TOOL

python3 scripts/create_mission_archive.py \
  --mission-name "Audio PX4 Sync Test" \
  --operator "Operator Name" \
  --drone drones/D0012.yaml \
  --profile profiles/audio_px4_sync_test.yaml \
  --code-root /absolute/path/to/mission-code-repo \
  --initialize-drone \
  --drone-host root@192.168.0.20 \
  --remote-sync-root /home/root/halo_sync_test
```

The command prints the canonical mission/session ID, both paths, and the generated
`metadata/next_commands.sh` path. Replace the example `--code-root` with the actual
Git working tree; omit it to retain automatic discovery. The generated command file
contains the exact mission paths and ID for checking the drone, starting MicroDDS,
starting the configured recorder, listing ULogs, and collecting data.

To choose a fixed ID instead:

```bash
python3 scripts/create_mission_archive.py \
  --mission-name "Audio PX4 Sync Test" \
  --mission-id 20260820_143000_UTC_audio_px4_sync_test_D0012 \
  --operator "Operator Name" \
  --drone drones/D0012.yaml \
  --profile profiles/audio_px4_sync_test.yaml \
  --initialize-drone
```

### 2. Start MicroDDS and the ReSpeaker recorder with the same ID

Use the generated guide's `start-microdds` section. Set
`RESPEAKER_RECORDER_COMMAND` to the launcher already installed on the drone, then use
its `start-respeaker` section. The guide adds `--session-id <mission_id>` and does not
start by itself.

Pass the printed `mission_id` unchanged as the recorder's `session_id`. Do not create a
second timestamp or shorten the value. The intended invariant is:

```text
ground folder name == drone folder name == recorder session_id == metadata mission_id
```

### 3. Conduct the mission

Follow the selected profile. For the included audio/PX4 synchronization profile:

1. Start audio recording first.
2. Wait until the recorder confirms `Recording WAVE...`.
3. Arm using the remote only when the real test is ready and approved, then conduct the
   planned test. Arming is unnecessary for archive dry tests; remove props for bench
   arming unless this is an approved flight test.
4. Disarm safely.
5. Keep recording briefly after disarm, then stop the recorder cleanly.
6. Record the true termination reason and any anomalies during collection.

### 4. Identify the PX4 ULog path or paths

ULogs normally live under `/data/px4/log`. For example:

```bash
ssh root@192.168.0.20 \
  "LC_ALL=C LANG=C find /data -name '*.ulg' -printf '%T@ %p\n' | sort -n | tail -20"
```

Choose the ULog or ULogs belonging to this mission; do not assume the newest file is
correct without checking timestamps.

### 5. Collect the mission

Set the ID printed by the creator, then run collection:

```bash
MISSION_ID="20260820_143000_UTC_audio_px4_sync_test_D0012"
MISSION_DIR="$HOME/MIC_ARRAY_ROS/HALO_ARCHIVE/$MISSION_ID"

python3 scripts/collect_drone_data.py \
  --mission-dir "$MISSION_DIR" \
  --drone-host root@192.168.0.20 \
  --remote-sync-root /home/root/halo_sync_test \
  --ulog /data/px4/log/example.ulg \
  --termination-reason "completed normally" \
  --notes "Nominal ReSpeaker/PX4 synchronization test"
```

Do not provide `--session-id` in the normal workflow. The collector reads `mission_id`
from `mission_metadata.json` and uses it automatically.

For multiple ULogs, repeat the option:

```bash
python3 scripts/collect_drone_data.py \
  --mission-dir "$MISSION_DIR" \
  --ulog /data/px4/log/flight-1.ulg \
  --ulog /data/px4/log/flight-2.ulg \
  --termination-reason "completed normally"
```

`rsync -av` copies data; it does not delete the drone-side originals. Collection
always saves the ten newest candidates in `metadata/ulog_candidates_remote.txt`. When
every `--ulog` option is omitted, only candidates at or after the mission start are
eligible for automatic copying. Audio-only orchestrator runs disable auto-copy by
default; `--auto-ulog` explicitly enables it, while `--no-auto-ulog` is always safe.

### 6. Add external ROS bags or other raw data

ROS2 bags created by `halo_drone_mission_agent.py` are already included in the complete
mission-folder copy. For standalone recovery only, if a bag was recorded somewhere
outside the canonical drone mission folder, copy it into the designated ground folder.
Example:

```bash
rsync -av --rsync-path='LC_ALL=C LANG=C rsync' \
  root@192.168.0.20:/path/to/mission_bag/ \
  "$MISSION_DIR/drone_data/ros_bags/"
```

Place other original sensor files under `drone_data/raw_sensor_data/`. Record manual
transfers in operator notes or a report so their provenance is clear.

### 7. Verify the archive before clearing the drone

```bash
find "$MISSION_DIR" -maxdepth 4 -type f -print | sort

python3 -m json.tool \
  "$MISSION_DIR/metadata/mission_metadata.json"

python3 -m json.tool \
  "$MISSION_DIR/metadata/${MISSION_ID}_collection_manifest.json"
```

Confirm at minimum:

- The folder name equals `mission_id` in mission metadata.
- ReSpeaker/session files are present under `drone_data/audio/<mission_id>/`.
- Every expected `.ulg` is present under `drone_data/px4_logs/`.
- Required ROS bags and other raw sensor files are present, if the mission expected them.
- Status snapshot JSON files exist under `drone_data/status_logs/`.
- `warnings` and `errors` have been reviewed.
- `termination_reason` and operator notes are correct.

Only after verification and backup should remote mission data be considered safe to
remove. These tools do not delete remote data.

## Session override behavior

`--session-id` exists only for recovery or legacy cases where the recorder used the
wrong remote folder name. If it differs from `mission_id`:

- The collector prints and records a warning.
- The override selects the remote source folder.
- The local destination remains `drone_data/audio/<mission_id>/`.
- The manifest records both the canonical and effective remote folders.

Do not use the override during a normal mission; fixing the identity before recording
is safer than reconciling mismatched folders afterward.

## Overwrite protection

The creator refuses to modify an existing ground mission folder by default. `--force`
explicitly permits replacement of the exact ground folder and should be used only when
the existing contents are known to be disposable.

Remote initialization uses `mkdir -p` and rsync. It does not erase the remote mission
folder first, so reusing an ID can merge or replace same-named setup files. The safest
practice is one new mission ID per mission and no reuse.

Collection may merge files into an existing local audio session folder when rerun.
Review the collection history and timestamps whenever collection is repeated.

## Troubleshooting

### The collector says the folder name does not match `mission_id`

The ground folder is not the canonical folder recorded in metadata. Do not rename the
archive casually. Locate the correct archive or repair the mismatch only after checking
both ground and drone identities.

### SSH or rsync fails

Check network and authentication first:

```bash
ping -c 2 192.168.0.20
ssh root@192.168.0.20 "LC_ALL=C LANG=C hostname"
```

Initialization failures are saved under `drone_initialization.errors`. Collection
transfer failures are saved in the collection manifest and `run_status.errors`. Each
script performs a clear SSH check before its batch unless `--skip-ssh-check` is used.
For repeated password prompts, follow [SSH key setup](docs/SSH_KEY_SETUP.md). Remote
commands are prefixed with `LC_ALL=C LANG=C` to reduce locale warnings without changing
the drone's system locale.

### The drone agent compatibility or startup check fails

The orchestrator records the remote `python3 <agent> --help` result before launch. A
failure prevents recording from starting, sets `drone_agent_preflight_check_failed`,
and still attempts collection so the remote README, config, and console/status logs are
preserved. A launched process must also produce a start/status JSON record and remain
alive through the short startup window; otherwise collection runs with
`drone_agent_startup_confirmation_failed`.

### Git fields are empty

The creator could not find a Git repository from the current working directory or the
script location, or Git could not read the repository. Supply
`--code-root /absolute/path/to/the/repository` when the mission code is elsewhere. The
condition remains a warning; the script SHA-256 is still preserved.

### A service-status command returns nonzero

An unavailable or inactive service is preserved as a warning with its output. Review
the JSON command result before deciding whether it affected the mission.

### The ULog list is empty

Check `/data/px4/log`, flight timestamps, PX4 logging configuration, available storage,
and whether the vehicle actually armed. An empty `px4_logs/` directory means no ULog was
copied, not that the mission had no relevant flight-controller data.

## Command reference

Creator options:

- `--mission-name`: required human-readable mission/test name.
- `--mission-id`: optional fixed canonical folder/session ID.
- `--operator`: required operator name.
- `--drone`: required drone YAML path.
- `--profile`: required flight-profile YAML path.

## Validated five-drone passive ground archive workflow

The validated D0012 ground-bag path remains unchanged in
`scripts/run_halo_mission.py`. Ground Station A remains the only flight-control
station. Ground Station B runs one independent fixed-domain worker process per
drone; it never arms, takes off, flies, lands, disarms, or sends trajectory
commands.

Use `scripts/launch_halo_swarm.sh` from one ordinary terminal. It creates one
common mission archive and starts five background jobs. The previous
`scripts/launch_halo_swarm_terminals.sh` name remains as a compatibility wrapper;
no graphical terminals are required.

Each launch is a separate Bash subshell. The environment is fixed before the
worker is `exec`'d, and the parent captures the background PID immediately:

```bash
(
  set -euo pipefail
  cd "$REPO_ROOT"
  source /opt/ros/jazzy/setup.bash
  source ~/MIC_ARRAY_ROS/px4_ros2_jazzy_ws/install/setup.bash
  export ROS_DOMAIN_ID=3
  export ROS_LOCALHOST_ONLY=0
  export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
  export ROS_STATIC_PEERS=192.168.0.20
  export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
  exec python3 scripts/run_halo_drone_worker.py ...
) > "$MISSION_DIR/drones/D0012/status_logs/worker_console.log" 2>&1 &
PID_D0012=$!
```

The launcher performs this pattern five times concurrently for the fixed lab
mapping:

```text
D0012 | 192.168.0.20 | ROS_DOMAIN_ID 3 | ROS_STATIC_PEERS 192.168.0.20
D0013 | 192.168.0.21 | ROS_DOMAIN_ID 4 | ROS_STATIC_PEERS 192.168.0.21
D0014 | 192.168.0.22 | ROS_DOMAIN_ID 5 | ROS_STATIC_PEERS 192.168.0.22
D0015 | 192.168.0.23 | ROS_DOMAIN_ID 6 | ROS_STATIC_PEERS 192.168.0.23
D0016 | 192.168.0.24 | ROS_DOMAIN_ID 7 | ROS_STATIC_PEERS 192.168.0.24
```

Because each worker has its own subshell, exports for one domain cannot affect
another worker. Each worker writes only to its own mission folder, including:

```text
<mission_dir>/drones/D0012/status_logs/worker_console.log
<mission_dir>/drones/D0013/status_logs/worker_console.log
<mission_dir>/drones/D0014/status_logs/worker_console.log
<mission_dir>/drones/D0015/status_logs/worker_console.log
<mission_dir>/drones/D0016/status_logs/worker_console.log
```

Inspect a worker with `tail -f <path>`. The launcher also prints `jobs -l`,
tracks all five `$!` PIDs, monitors every `worker_status.json`, and waits for
each worker independently. A nonzero D0014 exit is recorded without terminating
D0012, D0013, D0015, or D0016.

Every worker uses:

```bash
source /opt/ros/jazzy/setup.bash
source ~/MIC_ARRAY_ROS/px4_ros2_jazzy_ws/install/setup.bash
export ROS_DOMAIN_ID=<that drone's actual domain>
export ROS_LOCALHOST_ONLY=0
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
export ROS_STATIC_PEERS=<that drone's IP address>
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

The preflight order is deliberate: CHECK DRONE ROS TOPICS FIRST. The worker
SSHs to its drone, sources `/opt/ros/foxy/setup.bash`, sets its fixed domain,
restarts/checks that drone's ROS 2 daemon, and confirms at least
`/fmu/out/sensor_combined`, `/fmu/out/vehicle_status`, and `px4_msgs` types.
Only after that does the ground-side worker use Jazzy, restart/check its own
fixed-domain discovery, confirm ground `/fmu` topics, and validate `px4_msgs`
decoding. A missing `ros_domain_id` fails preflight; it is never guessed.

The default READY barrier requires all five workers. The launcher prints
`SWARM ARCHIVE READY` only after all five status files report `phase=READY` and
all worker PIDs are still alive. `--allow-partial-swarm` permits ready workers
to continue after another worker has failed, with the failure retained in the
manifests. Ctrl-C sends SIGINT to each live archive worker, allowing active bags
to finalize, waits for them, records launcher termination, and never sends a
flight command. SIGKILL is not used for normal cleanup.

The ground bag is not started before flight. A worker observes
`/fmu/out/vehicle_status` and starts `ros2 bag record -a` only on a confirmed
ARMED transition. It prefers `/fmu/out/vehicle_land_detected` with `landed: true`,
records the configured 2–5 second `post_landing_record_s` post-roll (default 3),
and stops the bag with SIGINT for clean metadata finalization. If that topic is
unavailable, ARMED-to-DISARMED is the recorded `disarmed_fallback` stop trigger.
Each bag is written to:

```text
drones/<drone_id>/ros_bags/<mission_id>__<drone_id>_ground_rosbag/
```

ULog search/copy runs independently for every drone, so one connection or
collection failure does not stop the other workers. Audio remains optional;
disabled audio does not run `arecord` and is not treated as a missing file.
Every mission writes `metadata/swarm_manifest.json` and every drone writes
`drones/<drone_id>/metadata/collection_manifest.json`, including partial failures.

Safe configuration-only dry run; this does not SSH, start ROS, create an archive,
or send any flight command:

```bash
scripts/launch_halo_swarm.sh \
  --mission-name "swarm_test_001" \
  --operator "Operator Name" \
  --dry-run
```

A live no-flight preflight uses the same background-worker launcher and stops
workers after the READY checks:

```bash
scripts/launch_halo_swarm.sh \
  --mission-name "swarm_test_001" \
  --operator "Operator Name" \
  --preflight-only
```

After the five SSH aliases and fixed domain mapping are confirmed, the lab command is:

```bash
scripts/launch_halo_swarm.sh \
  --mission-name "swarm_test_001" \
  --operator "Operator Name" \
  --duration 180 \
  --enable-audio
```
